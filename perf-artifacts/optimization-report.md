# CodingFire Go 性能优化记录

## 主要原因

`internal/data/monitor.go` 的 `heartbeatMs = 4000` 被直接传给
`time.AfterFunc`。Go 将整数解释为纳秒，因此请求的间隔是 4 微秒，而非原意的
4 秒。实际扫描次数受系统定时精度、扫描耗时和合并逻辑影响；这不是精确的
“每秒 25 万次扫描”，但会反复触发扫描和补扫。

修复为 `heartbeatInterval = 4 * time.Second`，由单个调度协程管理启动扫描和
周期扫描。停止后不再安排新扫描；文件变化仍可立即请求扫描。

## 其他优化

- 已读完的、已有有效事件的 JSONL 文件，在打开文件和分配两个 256 KiB 缓冲区之前返回；保留部分行、追加、截断和手动重扫语义。
- 火焰维持 10 fps，余烬降为 4 fps；隐藏不安排重绘，熄灭只在状态变化时绘制。重新显示或点燃会立即请求新帧。
- 使用本地 go-gui 扩展 `UpdateImage`，复制到可复用的 CPU 缓冲区，并用 `glTexSubImage2D` 更新同一张纹理。过去的实现会让 GPU 缓存保留最多 128 张历史火焰纹理。该 API 支持 GL 和软件渲染，调用须在 GUI 线程上进行。
- 颜色不变时复用调色板；移除光晕计算中可代数消去的平方根。
- 历史记录逐行解析，不再先生成整份文本行数组；读取不完整时不压缩原文件，避免损失未读取的内容。近期事件查询不再按全部历史事件数量预分配。

## 验证结果

环境：Windows amd64，Go 1.27.1，AMD Ryzen 7 5800H。
下表是一次本机微基准对比，不能直接换算成整机 CPU/GPU 占用或进程常驻内存。

| 测试 | 修改前 | 修改后 |
|---|---:|---:|
| 未变化 JSONL：耗时/次 | 91,871 ns | 20,660 ns |
| 未变化 JSONL：分配字节/次 | 525,453 B | 288 B |
| 未变化 JSONL：分配次数/次 | 8 | 2 |
| 火焰合成：耗时/帧 | 1,586,349 ns | 1,586,679 ns |
| 火焰合成：分配次数/帧 | 1 | 0 |

单帧合成耗时基本持平；主要收益来自停止扫描空转、减少不必要帧、减少分配和复用纹理。

已通过：

- 主项目 `go test ./...`、`go vet ./...`。
- go-gui 的 `gui`、GL 和软件后端测试。
- 虚拟时钟验证：250 ms 启动扫描，4 秒周期扫描，事件即时扫描，停止后不再扫描。
- JSONL 追加、部分行、截断、手动重扫和无事件游标恢复；历史保留与不完整文件保护。
- 帧调度验证：燃烧/余烬/隐藏/熄灭，以及重新显示和点燃。
- 原生 Windows OpenGL 测试：隐藏测试窗口，连续更新 300 帧，纹理 ID 不变且缓存仅一项；从 GPU 读回的像素与输入一致，修改尺寸后仍正确。
- `--render` 输出的 7 张火势图、悬浮卡片和托盘图，共 9 张 PNG，与修改前 SHA-256 完全一致。

基准原始输出：`bench-before.txt`、`bench-after.txt`。
修改前源码保存在 `original/`，修改前可执行文件也保留在本目录。

## 运行新版本

产物：`../dist/CodingFire.exe`。

检查时系统已有一个 CodingFire 进程，路径为
`D:\BaiduNetdiskDownload\CodingFire-win-x86-v1.0.4\CodingFire.exe`，
并不是此项目 `dist` 下的新产物。此次没有替换该路径的程序或停止该进程。
请从托盘退出旧副本，再启动新产物，避免同时运行两个版本干扰占用比较。

整机 CPU/GPU 使用率、进程常驻内存和风扇转速未做同场景前后实测。
建议使用任务管理器比较启动后扫描完成、正常燃烧和隐藏火焰三个状态。

## 复现 GPU 检查

从项目目录运行（需 Windows OpenGL 环境，测试窗口不会显示）：

```powershell
$env:CODINGFIRE_GL_TEST = '1'
go test github.com/go-gui-org/go-gui/gui/backend/gl -run TestDynamicTextureGPU -v -count=1
```
